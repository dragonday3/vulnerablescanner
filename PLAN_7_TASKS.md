# PLAN_7_TASKS.md — VulnSight Phase 7 Task-Based Execution Plan

Companion to `PLAN_7.md` (narrative plan, binding authority for anything
a task here doesn't fully specify).

Scope: Phase 7 (Risk Intelligence / VRPS scoring) only — new
`risk_score`/`risk_tier` columns on `Asset` and `Scan`, the pure scoring
functions in `backend/app/modules/risk/`, the `risk_scorer.py`
orchestrator wired into the already-reserved `ScanStatus.RISK_ANALYSIS`
stage, and the read-only API/frontend surfacing. No Phase 8 (reporting)
work, no scoring-config override API, no re-scoring on validation-state
change.

## Global Constraints

1. **Migration-first ordering.** Task 1 (columns + migration) must land
   before Task 3 (the orchestrator writes into them) and Task 4 (the API
   reads them).
2. **Zero new network/Redis surface.** This phase reads only
   already-persisted `Finding`/`Misconfiguration` rows. If any file in
   this phase opens a socket, makes an HTTP/other request, or touches
   Redis, that's a Critical finding, not a style nitpick — contrast
   Phase 4's NVD client and Phase 6's TLS inspector, both deliberate,
   reviewed exceptions to a rule this phase does not get to claim.
3. **No changes to `discovery/`, `fingerprinting/`, `vulnerability/`, or
   `misconfiguration/` modules.** This phase reads their persisted
   output only (`Finding`, `Misconfiguration` rows via existing
   relationships) and writes exclusively to the new `Asset`/`Scan`
   columns.
4. **`risk_scorer.py`'s `score_assets` takes `scan`, not just `assets`
   — this is deliberate, not a regression of the "never touch scan"
   discipline.** The inherited rule from `correlator.py`/`analyzer.py`
   is "never mutate `scan.status`", not "never touch `scan` at all".
   Any write to `scan.status` inside `backend/app/modules/risk/` is a
   Critical finding; the `scan.risk_score`/`scan.risk_tier` writes are
   not — they are this function's entire second half.
5. **Risk-scoring failures can never flip a scan to `FAILED`.** Same
   best-effort contract as `FINGERPRINTING`/`ANALYZING`/`CORRELATING` —
   `tasks.py`'s new `RISK_ANALYSIS` block catches, logs, rolls back, and
   falls through; `risk_scorer.py` itself never lets one asset's scoring
   failure abort scoring of the rest (its own per-asset try/except).
6. **`risk_score`/`risk_tier` are nullable on both `Asset` and `Scan`,
   with no backfill.** `NULL` means "not yet risk-scored" and must stay
   distinguishable from a computed `0.0`/`"NONE"` ("scored, nothing
   found") — never conflate the two. An asset with zero findings/
   misconfigs must land on `0.0`/`"NONE"`, not be left `NULL`.
7. **`risk_tier` reuses the exact existing `CRITICAL`/`HIGH`/`MEDIUM`/
   `LOW`/`NONE` vocabulary** (`Finding.severity`/
   `Misconfiguration.severity`'s own convention) as a plain
   `String(20)`, not a DB enum. Frontend reuses the existing `Severity`
   type and `SeverityBadge` component unchanged — don't invent a
   parallel type/component.
8. **All scoring constants live in `scoring_config.py`, nowhere else.**
   No magic numbers inline in `scoring.py`/`risk_scorer.py`. No
   DB-backed config table, no override API/route this phase — that's a
   deliberate scope limit, not an oversight to "helpfully" fix.
9. **`FALSE_POSITIVE` findings contribute exactly `0.0`.** This is the
   one hard rule from `PLAN_5.md`'s own stated expectation for this
   phase — don't soften it into a discount.
10. **No `Service`-level persisted score, no new `ScanStatus` value, no
    bulk/manual re-score endpoint.** Don't add any of these "for
    completeness" — see `PLAN_7.md`'s Scope limits.
11. Follow established Phase 0-6 conventions: thin routes, business
    logic in `services`/`modules`, SQLAlchemy 2.x `Mapped`/
    `mapped_column` style, ruff/black/mypy clean on backend, `next lint`/
    `tsc --noEmit` clean on frontend, migrations never import
    application code (trivial here: pure `ADD COLUMN`, no backfill).
