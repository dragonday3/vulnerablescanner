# PLAN_6_TASKS.md — VulnSight Phase 6 Task-Based Execution Plan

Companion to `PLAN_6.md` (narrative plan, binding authority for anything
a task here doesn't fully specify).

Scope: Phase 6 (Misconfiguration Analysis) only — the new
`Misconfiguration` model + migration, three check families (header,
exposed-service, TLS-certificate), the `analyzer.py` orchestrator wired
into a new `ScanStatus.ANALYZING` stage, the read-only API/frontend
surfacing. No Phase 7 (risk scoring) work, no validation-state workflow
for misconfigurations.

## Global Constraints

1. **Migration-first ordering.** Task 1 (model + migration) must land
   before Task 5 (API nesting reads the new table) and Task 4 (the
   analyzer writes rows into it).
2. **Task 2 (header + exposed-service checks) and Task 3 (TLS
   inspection) are independent and touch disjoint files** — no shared
   file between them, both depend only on Task 1's `MisconfigCandidate`/
   model, neither depends on the other. Dispatched sequentially per the
   skill's "never dispatch multiple implementers in parallel" rule, but
   there is no ordering requirement between them; Task 4 is the only
   task that imports from both.
3. **No generic banner-grabbing.** `exposed_service_checks.py` is a
   static port→label table lookup only — it never opens a connection.
   The only new network call this entire phase introduces is
   `tls_inspector.py`'s TLS handshake. If any other file in this phase
   opens a socket or makes an HTTP/other request, that's a Critical
   finding, not a style nitpick.
4. **`tls_inspector.py` mirrors `http_prober.py`'s security posture**:
   a genuine per-connection timeout via `socket.settimeout`, no
   credentials sent, passive evidence only, and `verify_mode=ssl.CERT_NONE`
   / `check_hostname=False` are deliberate (the entire point is reading
   certs normal validation would reject) — never "fixed" to
   `CERT_REQUIRED` or flagged as a vulnerability in review.
5. **Analysis failures can never flip a scan to `FAILED`.** Same
   best-effort contract as `FINGERPRINTING`/`CORRELATING` — `tasks.py`'s
   new `ANALYZING` block catches, logs, rolls back, and falls through;
   `analyzer.py` itself never lets one service's failure abort the
   rest (its own per-service try/except, mirroring `correlator.py`'s
   per-CPE isolation).
6. **No changes to `discovery/`, `fingerprinting/`, or `vulnerability/`
   modules.** This phase reads their persisted output only.
   `tls_inspector.py`'s `TLS_CANDIDATE_PORTS` is an independent constant,
   not an import of `http_prober.py`'s private `_TLS_HEURISTIC_PORTS`.
7. **No `validation_state`/`confidence_score`-style columns on
   `Misconfiguration` this phase.** Detection only — don't add fields
   "for consistency" with `Finding`. No PATCH route, no new frontend
   control.
8. **`Misconfiguration.severity` is a plain `String(20)`, not a DB
   enum** — mirrors `Finding.severity`'s existing convention exactly.
9. **One check per `(service_id, check_id)`.** The
   `uq_misconfig_service_check` unique constraint is load-bearing — the
   analyzer must never attempt the same `check_id` twice for one
   service in a single run (e.g. `exposed-sensitive-service` fires at
   most once per service even though the lookup table has many ports —
   a service only has one `port`).
10. **New runtime dependency this phase: `cryptography`.** Added to
    `backend/requirements.txt`, pinned `~=` against the version actually
    verified working in this project's Docker image (check
    `pip show cryptography` after installing, don't guess a version
    number) — same convention as every existing pin in that file.
11. **Frontend reuses the existing `Severity` type and `SeverityBadge`
    component unchanged.** Don't create a parallel severity type/badge
    for misconfigurations.
12. Follow established Phase 0-5 conventions: thin routes, business
    logic in `services`/`modules`, SQLAlchemy 2.x `Mapped`/
    `mapped_column` style, ruff/black/mypy clean on backend, `next lint`/
    `tsc --noEmit` clean on frontend, migrations never import
    application code (trivial here: pure `CREATE TABLE`, no backfill).

## Task 1: `Misconfiguration` model + migration

Create `backend/app/models/misconfiguration.py` (the `Misconfiguration`
model, exactly as specified in `PLAN_6.md` §1). Edit
`backend/app/models/service.py`: add the `misconfigurations` relationship
and its `TYPE_CHECKING` import.

Generate an additive migration (`down_revision` = current head —
re-verify it's still `8f08312a037b` by reading
`backend/migrations/versions/` directly before generating; the plan's
own stated value may be stale by the time this task runs):
`alembic revision --autogenerate -m "add misconfigurations table"`. No
hand-edit should be needed (pure `CREATE TABLE`, no backfill, no
pre-existing rows to touch) — if the autogenerated migration contains
anything beyond creating the table/constraint/FK, review it carefully
before accepting it as-is.

**Tests**: none standalone beyond a smoke check (covered by Task 4/5's
tests exercising the new table via the ORM/API).

**Acceptance**: migration applies cleanly against a database carrying
pre-existing `Service`/`Finding` rows, with no data loss to any
existing table; `docker compose exec postgres psql -U vulnsight -d
vulnsight -c "\d misconfigurations"` shows all columns with the
documented types/nullability and the `uq_misconfig_service_check`
constraint; `ruff`/`black`/`mypy` clean.

## Task 2: Header checks + exposed-service checks

Create `backend/app/modules/misconfiguration/checks.py` (the
`MisconfigCandidate` dataclass, per `PLAN_6.md` §2).

Create `backend/app/modules/misconfiguration/header_checks.py`
(`check_headers`) and `backend/app/modules/misconfiguration/exposed_service_checks.py`
(`SENSITIVE_PORTS`, `check_exposed_service`), per `PLAN_6.md` §2's exact
check tables. Both are pure functions — no DB session, no network, never
raise. Not wired into `tasks.py` yet (Task 4 does that, after Task 3
also exists) — these two modules just need to exist and be independently
correct and tested.

**Tests** (`backend/tests/test_header_checks.py`,
`backend/tests/test_exposed_service_checks.py`, both new): one test per
check_id (triggered and not-triggered) per `PLAN_6.md` §7, plus the
defensive "no `headers` key at all / `evidence=None` → empty list, no
raise" case for `check_headers`, plus a "port not in `SENSITIVE_PORTS` →
`None`" case for `check_exposed_service`.

**Acceptance**: `pytest -v` green; every check_id in both modules
covered by at least one triggered and one not-triggered test; `ruff`/
`black`/`mypy` clean; no test touches Redis/network/DB (neither module
has any such dependency).

## Task 3: TLS certificate inspection

Add `cryptography` to `backend/requirements.txt` (pinned per Global
Constraint 10 — verify the actual installed version before writing the
pin, don't guess). Create
`backend/app/modules/misconfiguration/tls_inspector.py` (`TlsInspectionResult`,
`_inspect_port`, `inspect_tls`, `check_tls_result`), per `PLAN_6.md` §3's
exact spec, constants, and check table. Not wired into `tasks.py` yet
(Task 4).

**Tests** (`backend/tests/test_tls_inspector.py`, new): per `PLAN_6.md`
§7 — `check_tls_result` tested with plain constructed `TlsInspectionResult`
fixtures (self-signed, expired, expiring-soon, weak-protocol, and a
clean/no-findings case — confirm `expired-cert` and `expiring-soon-cert`
are mutually exclusive). `inspect_tls`/`_inspect_port` tested against a
**real** local TLS listener (generate a throwaway self-signed cert with
`cryptography` itself, serve it via a `socket`+`ssl`-wrapped local TCP
server fixture in the test) — not a mock of `ssl`/`socket`. Check this
repo for an existing TLS-test-fixture pattern before inventing one; if
none exists, this is the first. Also test the genuine failure path
(nothing listening on a port, or a non-TLS port) returns `None`, not a
raised exception.

**Acceptance**: `pytest -v` green, including at least one test against
a real handshake (not fully mocked); `ruff`/`black`/`mypy` clean;
`cryptography`'s pin in `requirements.txt` matches a version actually
verified installed and working.

## Task 4: Analyzer orchestrator + `ANALYZING` stage wiring

Create `backend/app/modules/misconfiguration/analyzer.py`
(`analyze_services`), per `PLAN_6.md` §4 — importing from `checks.py`,
`header_checks.py`, `exposed_service_checks.py` (Task 2), and
`tls_inspector.py` (Task 3). This is the one place all three check
families meet; re-read `PLAN_6.md` §4's exact 3-step description before
writing it.

Edit `backend/app/workers/tasks.py`: insert the new `ANALYZING` stage
between the existing Step 9 (HTTP fingerprinting) block and the existing
`scan.status = ScanStatus.CORRELATING` line, per `PLAN_6.md` §4's exact
code shape. Re-read the real current file first — step numbers/line
numbers may have shifted; don't blindly trust the plan's stale
line-number references.

**Tests** (`backend/tests/test_analyzer.py`, new): per `PLAN_6.md` §7 —
a correlator.py-style test with 2+ services where one service's check
input is deliberately malformed (simulating a failure) and the other
service's misconfigurations are still correctly persisted, proving
per-service isolation rather than asserting it. A test confirming
`uq_misconfig_service_check` is actually respected (the analyzer never
attempts a duplicate `check_id` for one service even if, say,
`check_exposed_service` were somehow called twice). Extend
`backend/tests/test_scans.py` or add a worker-level test confirming a
scan with a deliberately-unreachable TLS target still reaches
`COMPLETED`, not `FAILED` (the best-effort contract, exercised, not
just asserted).

**Acceptance**: `pytest -v` green; `ruff`/`black`/`mypy` clean; a scan
against a target with at least one of each check family's trigger
condition produces the exact expected `Misconfiguration` rows (verified
via `docker compose exec postgres psql`), and the scan reaches
`COMPLETED`.

## Task 6: Full-stack verification pass

Fresh `docker compose down -v && docker compose up --build`. Apply the
migration. Run `PLAN_6.md` §8's full Verification Plan end-to-end: a
real scan against a target exposing at least one condition from each
check family — confirm the exact expected `Misconfiguration` rows
(`check_id`/`severity`/`evidence`) persist; confirm a scan that includes
a deliberately-broken/unreachable TLS target still reaches `COMPLETED`;
confirm `GET /scans/{id}/assets`'s nested `misconfigurations` shape;
confirm the frontend results page renders the new block. Run the full
backend suite and lint/type-check on both sides.

This is not a feature-writing task — fix only narrow integration issues
found (same scope discipline as every prior phase's final task). If
something reveals an architectural gap rather than an integration
correction (e.g. the `SENSITIVE_PORTS` table or header-check set turns
out to need real-world expansion), report BLOCKED/NEEDS_CONTEXT instead
of improvising a redesign.

**Acceptance**: every step in `PLAN_6.md` §8 passes as described;
`pytest -v`, `ruff check .`, `black --check .`, `mypy app`, `npm run
lint`, `npx tsc --noEmit` all green; report the full transcript/evidence
for each check family, including the actual persisted row(s) so a
reviewer can independently verify correctness.
